# BuildPath — статус реализации

Срез на 9 ноября 2026 года, дополнен 12 ноября (раздел ниже). Это фактический статус кодовой базы, а не обещание готовности к production. Полный порядок работ задан в [IMPLEMENTATION_ROADMAP.md](IMPLEMENTATION_ROADMAP.md).

## Кратко

Есть рабочий путь конструктора по этапам для одностраничного сайта и сайта компании: от цели до собранной и проверенной страницы, которую можно скачать. ИИ выполняет этапы по инструкциям владельца, без ИИ работают формы и шаблоны. Готовый сайт можно опубликовать на поддомен BuildPath и получать заявки с формы в Telegram или на почту. На этап можно пригласить специалиста: он направляет ИИ и отправляет результат на приёмку, видя только свой этап. Этапы можно вести и в Telegram: в боте кнопками или в Mini App. Отдельно работает инструмент сверки сайта с требованиями и макетами. Развёртывание отложено до завершения разработки.

- **Почта:** Resend или Brevo (Brevo — без своего домена, с подтверждённого адреса).
- **Аккаунт:** «Забыли пароль?», повторная отправка письма с подтверждением, лимиты на вход, регистрацию и письма.

- **Команда проекта (13 ноября):** приглашение участников с ролями (администратор, исполнитель, проверяющий, наблюдатель) и правило согласования этапа несколькими проверяющими — любой один, все или заданное число, автор не одобряет свою версию (STAGE_WORK_MODEL.md, раздел 35).
- **Проверка перед публикацией (13 ноября):** каждая сборка проходит аудит страниц (безопасность, доступность, бюджеты веса, поисковики) по активному профилю качества (проекту можно выбрать свой, §49; профиль может требовать пороги Lighthouse, §50); непройденную сборку нельзя принять и опубликовать; что не измеряется — так и показано (STAGE_WORK_MODEL.md, раздел 36).
- **Мелочи (13 ноября):** защита форм сайтов без скриптов (метка времени, вопрос-пример по выбору владельца), кадрирование фото и галереи до 12 фото в блоке, голосовые в боте (выключены без `BUILDER_AI_TRANSCRIBE_MODEL`; нужна правка политики), новое оформление «Сверки сайта» и консоли (STAGE_WORK_MODEL.md, раздел 37).
- **Веб-приложения (13 ноября):** новый тип проекта доводит до пакета для разработчика — функции и роли с критериями приёмки, экраны с кликабельным прототипом, архитектура с контрактом API; код приложения BuildPath не пишет (STAGE_WORK_MODEL.md, раздел 38).
- **Работа на этапах (13 ноября):** исполнители на выбранных этапах, проверка по очереди, замечания к материалам с блокирующими (STAGE_WORK_MODEL.md, раздел 39).

| ИИ-сверка | Готово с настройкой | Необходим OpenAI API key/model; результаты — предложения, не автоматическое одобрение ТЗ или backend. |
| Проверка ТЗ | Частично готово | Ручной checklist, статусы и доказательства. ИИ не выставляет статус требования. |
| Backend/API | Ограниченный probe | Только пользовательские GET/HEAD проверки с ожидаемым HTTP-статусом и необязательным JSON-path. Это не полный интеграционный или security-тест. |
| DOM/доступность | Ограниченный аудит | Эвристические счётчики и признаки; не полноценная WCAG-проверка. |
| Отчёты | Готово | JSON, автономный HTML, печать в PDF; включает покрытие, сигналы, страницы и ограничения. |
| Каталог и администрирование | Готово с ограничениями | Staff sign-in; каталог возможностей; управление версиями quality profiles; журнал аудита только для super admin и operations auditor с фильтрами, лимитом окна 90 дней и безопасной пагинацией. Управление данными проектов и release controls не реализованы. |
| Quality profiles и gate | Частично готово | Staff API и admin UI для профилей, черновиков и истории. Версия профиля фиксируется при создании review; проект может выбрать свой профиль (§49), иначе — профиль по умолчанию. Gate оценивает покрытие ТЗ, пользовательские API probes, доступность/SEO эвристики, HTTPS и выбранные security headers, навигационные timing/resource метрики. Нет vulnerability/dependency сканирования и Core Web Vitals настоящих посетителей; сборки конструктора проверяются Lighthouse в браузере (лабораторно; подсказка, если профиль не задаёт обязательные пороги — STAGE_WORK_MODEL.md §41, §50). Для сборок конструктора тот же профиль применяется к проверке перед публикацией и блокирует её (раздел 36). |

## Следующие необходимые работы

1. Расширить baseline до проверки уязвимостей, устойчивых performance budgets/Core Web Vitals и связать доказательства с release readiness; проектную публикацию пока не блокировать фиктивной проверкой.
2. Добавить project-level выбор quality profile и фиксировать выбранную активную версию в новых review.
3. Развернуть worker (разбор, браузерная проверка, сверка сайта) и ClamAV; проверить с настоящими Telegram, почтой, GitHub и платёжным провайдером.
4. Затем закрывать этапы продукта вертикально: интервью и требования → SiteSpec/детерминированная генерация → команда и approvals → deploy provider и quality gate.

## Ограничения текущей готовности

Рабочая сверка не означает готовность BuildPath как полного builder-продукта. Перед включением реальных пользователей потребуются environment configuration, миграция AI-поля, проверка изолированного worker egress, расширение quality evidence и подключение gate к release readiness, дальнейшее production-hardening staff boundary для admin, operational monitoring и end-to-end проверка развёрнутой инфраструктуры.
