# Полный путь продукта: от идеи до развития после запуска

Статус: **принято** (24 ноября 2026; владелец продукта поручил решить открытые вопросы по своему усмотрению — решения в разделе 10). Код по этому документу не меняется, пока владелец продукта его не примет. Дополнено 24 ноября: отслеживание хода работ в плане (4.8), инструкции и классы проверки, включая недобросовестного пользователя и безопасность (4.10), модель угроз в архитектуре (4.6). После принятия разделы переносятся в PRODUCT_REQUIREMENTS.md и TECHNICAL_SPECIFICATION.md, как сказано в CLAUDE.md.

Документ дополняет UNIFIED_PATH.md (восемь фаз) и STAGE_WORK_MODEL.md (как работает этап). Он отвечает на три вопроса:
1. Какие этапы нужны, чтобы идея человека стала готовым продуктом.
2. Как каждый этап описан одинаково: что он делает, как работает и когда считается выполненным.
3. Чего сейчас не хватает и в каком порядке это сделать.

## 1. Что хочет владелец продукта

- Человек приходит с идеей, часто сырой. Платформа старается понять её, уточняет, находит дыры и в итоге показывает идею понятными схемами и текстом.
- Платформа сама предлагает **дополнительные функции**, связанные с идеей. Человек решает, что из них брать.
- У человека может быть всё готово: описание, ТЗ, схемы. Тогда платформа не заставляет начинать заново. Она разбирает готовое, показывает пробелы и всё равно собирает **один понятный документ**, по которому любой читатель поймёт, что требуется.
- Дальше по цепочке: полное ТЗ → архитектура → план реализации по модулям (что делать параллельно, что последовательно) → контракты → реализация → проверка → запуск → развитие.
- **У каждого этапа одинаковое описание**: требования к работе этапа, как он работает и критерии приёмки.
- Отдельный вопрос — **закрытые сети и VPN**. Ответ в разделе 7.

## 2. Паспорт этапа: одинаковое описание для всех этапов

Каждый этап описывается одним шаблоном. Человек видит паспорт на странице этапа, специалист и ИИ работают по нему, а платформа проверяет результат по его правилам.

| Раздел паспорта | Что в нём | Где сейчас в коде |
|---|---|---|
| **Назначение** | Зачем этап и что без него пойдёт не так. Одна-две фразы простыми словами | `purpose` в каталоге этапов — есть |
| **Входы** | Принятые результаты, на которых строится этап, и минимальная полнота каждого. Чего не хватает — видно сразу | `inputs` — есть; минимальная полнота входа — частично (`stage-outputs`) |
| **Как работает** | Шаги этапа: разговор или импорт готового → черновик ИИ → проверка → уточнения → приёмка. Кто что делает: ИИ, владелец, специалист | В тексте этапа и плейбуке — частично; отдельного поля нет |
| **Результат** | Структура артефакта: поля, схемы, документ. Как он выглядит для человека и для следующего этапа | `outcome`, `artifactType` — есть |
| **Требования к результату** | Правила качества, которые проверяет программа: полнота, логика, безопасность, понятность | Проверка качества (`stage-review`) — есть для части этапов |
| **Критерии приёмки** | Что должно быть верно, чтобы этап приняли: автоматические проверки (блокируют) и чек-лист человека | `acceptance` + блокирующие замечания — есть |
| **Готово, когда** (Definition of Done) | Одна формулировка «этап выполнен», единая для владельца, специалиста и ИИ | Нет — добавить |
| **Что передаётся дальше** | Какие части результата нужны каким этапам. По этому списку решается, кому отправить уведомление об изменении | `stage-outputs` — есть |
| **Кто делает** | Уровень ИИ (делает сам / черновик / помогает), какой специалист нужен и когда, режим доступа по умолчанию | `ai.level`, рекомендация специалиста, режимы доступа — есть |
| **Если уже есть готовое** | Что можно загрузить (текст, файл, ссылка) и как платформа это разберёт | `importHint` — у части этапов |
| **Документ** | Как результат выглядит для чтения: PDF, Word, Markdown | Markdown у ТЗ; для других этапов нет |

Правило: **паспорт виден на странице этапа до начала работы**. Человек знает, что от него ждут и когда этап закончится. Специалист видит, за что ему платят.

Фазы — как в UNIFIED_PATH.md. Внутри фаз этапы перечислены по порядку. Обозначения: ✅ есть, ◐ есть частично, ➕ новый этап.

| 1.2 | **Разбор идеи** | ✅ | Проблема, для кого, ценность, альтернативы, как зарабатывает, допущения и риски, как понять успех |

### Сквозные части (не этапы, но нужны на каждом)

- **Словарь терминов** проекта. Собирается с первого этапа; ИИ и люди используют одни слова.
- **Журнал решений.** Что решили, почему и кто. Для архитектуры — в формате ADR. Сейчас решения есть в карточках выбора и объяснениях пропуска замечаний, но не собраны вместе.
- **Риски и допущения.** Появляются при разборе идеи, обновляются на каждом этапе. Риск без решения виден на карте проекта.
- **Документы для людей.** Концепция, ТЗ, архитектура, план, инструкция пользователя и администратора. Всё скачивается одним архивом.
- **Смета.** Растёт по мере уточнения: после идеи — вилка, после плана — по модулям.
- **Персональные данные и закон.** Какие данные храним, согласия, срок хранения. Уже проверяется в процессе; нужно протянуть до архитектуры (где хранятся) и запуска (политика конфиденциальности).

## 4. Паспорта новых и меняющихся этапов

### 4.1. Идея своими словами (замена «Цели» как первого шага)

- **Назначение.** Понять, что человек хочет, его же словами. Ничего не требовать заранее.
- **Входы.** Нет. Можно приложить что угодно: текст, ТЗ, схемы, ссылки на похожие продукты, голос.
- **Как работает.** Разговор: ИИ задаёт по одному вопросу и объясняет, зачем спрашивает. Если человек загрузил готовые материалы, ИИ сначала разбирает их и спрашивает только о пробелах. Тип проекта (сайт, магазин, приложение) платформа предлагает сама по рассказу.
- **Результат.** Паспорт идеи: название, суть в одном предложении, для кого, главная задача, тип проекта, исходные материалы.
- **Требования к результату.** Суть понятна без автора: проверяет ИИ-рецензент и правило «одно предложение, без жаргона». Тип проекта выбран.
- **Приёмка.** Человек подтверждает: «Да, это моя идея».
- **Готово, когда** человек, не знающий автора, прочтёт паспорт и правильно перескажет идею.
- **Дальше →** Разбор идеи, Бизнес-процесс.

**Сделано 26 ноября.** Этап `story` «Идея своими словами» (каталог маршрутов 1.18.0) — первый этап всех новых проектов.

- **Паспорт идеи.** Поля:
  - название;
  - суть в одном предложении (до 200 знаков);
  - для кого;
  - какую задачу это решает;
  - рассказ своими словами (до 3000 знаков, необязательно);
  - что уже есть: таблицы, ТЗ, ссылки (необязательно).

  Тип проекта выбран в мастере создания по рассказу и показан в паспорте.
- **Как заполнить.**
  - Разговором: ИИ спрашивает только о том, чего не хватает, а без ИИ задаёт вопросы паспорта по одному.
  - Вручную.
  - Вставить готовый текст: он сохраняется как рассказ.
  - Рассказ из мастера создания сразу стоит в поле «Расскажите своими словами» и предлагается первым ответом в разговоре.
  - Черновик без ИИ берёт название проекта и рассказ. Остальное ИИ не додумывает.
- **Проверка.** Правила:
  - суть в нескольких предложениях — важное замечание;
  - суть слишком короткая — важное замечание;
  - специальные слова (MVP, API, CRM, лендинг, юзер…) — мелкое замечание;
  - задача повторяет суть — мелкое замечание.

  Замечания — советы, принять этап они не мешают. ИИ-рецензент читает паспорт как посторонний.
- **Приёмка** — кнопка «Да, это моя идея».
- **Дальше.** Разбор идеи берёт из паспорта задачу и «для кого». Название, суть и «для кого» получают все этапы, которые раньше брали их из «Цели»: процесс, ТЗ, концепция, пакет для разработки, задание ИИ-агенту, `project.md`.
- **Сайты.** «Цель сайта» осталась вторым этапом: главное действие, контакты и тон. Её черновик берёт название, суть и «для кого» из паспорта, поэтому владелец дописывает только кнопку, контакты и тон.
- **Веб-приложения.** У новых веб-приложений «Цели» нет: этапы, построенные на ней, строятся на паспорте идеи.
- **Старые проекты не меняются.** Маршрут проекта — это этапы, которые у него есть. У проектов, созданных раньше, «Цель» остаётся первым этапом.
- **Почему не всё по решению §10.1.** Перенос главного действия и контактов в ТЗ сайта, а тона — в тексты отложен: «Цель» читают около 30 модулей сборки и публикации сайта (тексты, кнопки, форма заявки, быстрые правки, готовность к запуску). Переносить их ради формы без пользы для человека рискованно. Сайтовая «Цель» теперь занимается только сайтом, а идея описана отдельно.

### 4.2. Разбор идеи (сделан 24 ноября)

- **Назначение.** Довести идею до ясности и найти дыры раньше, чем на них потрачены деньги.
- **Входы.** Паспорт идеи.
- **Как работает.** ИИ раскладывает идею по полям ниже. Чего нет в рассказе, не выдумывает: помечает «не сказано» и задаёт вопрос. Для каждой дыры объясняет, чем она опасна. Человек отвечает, принимает допущение («пока считаем, что…») или откладывает.
- **Результат.**
  - Проблема и для кого. Сегменты пользователей, если их несколько.
  - Ценность: почему выберут вас.
  - Альтернативы и конкуренты: как люди решают задачу сейчас. Названные человеком; ИИ может предложить, с пометкой «предложение ИИ».
  - Как продукт зарабатывает или экономит. Для внутреннего инструмента — что экономит.
  - Допущения, риски и что их проверит.
  - Как понять успех: 1–3 измеримые цели («20 записей в неделю через сайт»).
  - Ограничения: срок, бюджет, закон, где должны храниться данные.
- **Требования к результату.** Поля заполнены или осознанно помечены «не знаю / позже». Риски с влиянием «высокое» без решения видны как блокирующие (правило как у «Вы это учли?»).
- **Приёмка.** Нет открытых блокирующих рисков. Цель успеха измерима.
- **Готово, когда** понятно, кому и зачем продукт, как поймём, что он работает, и какие риски приняты сознательно.
- **Дальше →** Бизнес-процесс, Предложения функций, План (риски), Запуск (цели успеха → аналитика).
- **Как сделано.** Этап `idea` (каталог 1.10.0) стоит после «Цели» во всех типах проектов и необязателен: владелец или менеджер может пропустить его с письменной причиной (`POST /projects/{id}/stages/idea/skip`). Причина сохраняется в этапе и в журнале (`stage_skipped`); пропущенный этап считается выполненным для следующих этапов и для итоговых файлов, к нему можно вернуться. Черновик без ИИ берёт группы клиентов из паспорта, остальное оставляет пустым. Проверка этапа: сильный риск без решения — блокирующее замечание, цель без числа — важное, неподтверждённая альтернатива от ИИ, нет альтернатив, нет дохода, группа без потребности, нет рисков, «проблема» описывает продукт — мелкие. На экране — «Идея на одном экране» и поля. Старые проекты не меняются: маршрут сохраняется при создании проекта. «Идея своими словами» как отдельный рассказ сделана 26 ноября (§4.1).

### 4.3. Предложения функций (сделан 25 ноября)

- **Назначение.** Человек не знает, что обычно бывает в таких продуктах. Платформа подсказывает, не навязывая.
- **Входы.** Разбор идеи, бизнес-процесс.
- **Как работает.**
  - Платформа берёт типовые возможности для отрасли и типа проекта из каталога: напоминания, отмена, отзывы, онлайн-оплата, личный кабинет, отчёты, роли сотрудников, уведомления.
  - ИИ отбирает подходящие и объясняет каждую: что даёт бизнесу, кому нужна, из какого шага процесса вытекает, сколько примерно добавит к сроку и цене.
  - Человек раскладывает предложения по колонкам: «в первую версию», «потом» или «не нужно».
  - Выбранное попадает в процесс (новые шаги) и в ТЗ.
- **Результат.** Список возможностей с решением и причиной.
- **Требования к результату.** Каждая предложенная возможность связана с шагом процесса или целью успеха. Возможности, которые платформа не умеет строить, помечены честно (каталог возможностей).
- **Приёмка.** Решение принято по каждой предложенной возможности.
- **Готово, когда** объём первой версии осознан: понятно, что в неё входит и что отложено.
- **Дальше →** ТЗ (функции и приоритеты), Бизнес-процесс (новые шаги — через уведомление об изменении).
- **Как сделано.** Этап `suggestions` (каталог маршрутов 1.11.0) стоит между бизнес-процессом и ТЗ во всех типах проектов и необязателен; пропустить его можно и до готовности входов. Каталог — 16 типовых возможностей в коде (`SUGGESTIONS_VERSION` 1.0.0). Черновик без ИИ предлагает то, чего **нет** в процессе (например, запись без напоминания), с основанием: шаг процесса или цель из разбора идеи. «Кто делает» (платформа на сайте / код приложения / аккаунт владельца в сервисе / пока не делает) определяет платформа по каталогу и типу проекта, ИИ этого изменить не может; свои предложения ИИ получают не больше чем «код приложения». Принять этап можно, когда по каждому предложению есть решение. Проверка: больше 6 возможностей в первой версии — важное замечание; у предложения ИИ нет основания — важное; нужен аккаунт, платформа пока не делает, «не нужно» без причины — мелкие. Черновик ТЗ берёт «в первую версию» как обязательные функции с начальным «готово, когда», «потом» — как функции на потом. Пока не сделано: новые шаги в процессе из выбранного (сейчас выбранное идёт только в ТЗ) и оценка срока и цены — вместо неё «немного / заметная / большая работа».

### 4.4. Концепция продукта (сделан 25 ноября, итог фазы «Идея»)

- **Назначение.** Один документ, который поймёт любой: инвестор, партнёр, разработчик, сотрудник.
- **Входы.** Паспорт идеи, разбор, процесс, функции.
- **Как работает.** Платформа собирает документ сама, ИИ только связывает текст. В документе есть оглавление, схемы процесса и данных, глоссарий и открытые вопросы. Если человек пришёл со своими материалами, документ всё равно собирается в этом виде, а источник каждой части указан.
- **Результат.** Документ (PDF, Word, Markdown) и его версия.
- **Требования к результату.**
  - Нет пустых разделов без пометки.
  - Каждая схема подписана.
  - Каждый термин, который не поймёт посторонний, есть в словаре.
  - Проверка «понятности»: ИИ-рецензент читает документ как посторонний и перечисляет, что ему непонятно.
- **Приёмка.** Владелец прочитал и подтвердил. По желанию — «показать другому человеку»: ссылка на чтение и комментарии.
- **Готово, когда** человек, не участвовавший в проекте, отвечает по документу на вопросы: что строим, для кого, что входит в первую версию.
- **Дальше →** ТЗ.
- **Как сделано.** Этап `concept` (каталог маршрутов 1.12.0) стоит после «Предложений функций» во всех типах проектов и необязателен; входы — паспорт, разбор идеи, процесс, предложения. Он не является входом ТЗ: концепция — документ для людей, а не основание следующих этапов. Документ собирает платформа из принятых этапов, которые видит смотрящий: в двух словах, проблема и для кого, почему выберут, как это работает (Схема 1 — процесс по сценариям), какие данные хранятся (Схема 2), первая версия и что потом, деньги-цели-риски, ограничения, словарь, открытые вопросы. У каждого раздела указан этап-источник; пустой раздел пишет почему («этап пропущен владельцем», «ещё не принят»). От владельца — «в двух словах», словарь, открытые вопросы, «что ещё важно»; черновик без ИИ берёт их из паспорта, разбора и нерешённых пунктов, ИИ пишет только их. Понятность: правило ищет термины без объяснения в словаре (важное замечание), ИИ-проверка читает весь документ как посторонний. Выгрузка: Markdown и Word (свой сборщик .docx, текст экранируется; схемы — только в PDF), PDF — страница печати со схемами; `concept.md` в выгрузке проекта. Словарь терминов пока распознаёт только русские тексты.

**Сделано 27 ноября — «Показать другому человеку».** Ссылка на концепцию для человека без аккаунта: партнёра, инвестора, будущего разработчика.

- **Кто включает.** Владелец или менеджер, на этапе «Концепция продукта», после сохранения. Ссылка вида `{адрес приложения}/concept/{токен}`.
- **Что видит читатель.** Последнюю сохранённую версию, собранную так, как её видит владелец. Правки владельца доходят сразу.
- **Что скрыто.**
  - Раздел «Деньги, цели и риски» скрыт сразу. Владелец может скрыть и другие разделы.
  - Вместе со скрытым разделом убираются его схема и полный Markdown документа.
- **Индексация.** Страница не индексируется поисковиками.
- **Замечания читателей.**
  - Читатель может оставить замечание: имя, раздел по желанию, текст до 1000 знаков. Замечания можно выключить.
  - Защита: поле-ловушка для ботов, не больше 10 замечаний в час с одного адреса и 100 в день на ссылку.
  - Замечания хранятся как обычный текст и ИИ не передаются. Их видит только команда проекта: в блоке ссылки и во «Входящих» владельца и менеджеров, пока их не отметят «Учтено».
- **Счётчик.** Считается, сколько раз ссылку открыли. Кто открывал, не сохраняется.
- **Новая ссылка или выключение.** Старая ссылка сразу перестаёт работать, счётчик обнуляется.
- **Нужно.** Заданный `PUBLIC_APP_URL` у API.

### 4.5. ТЗ (расширение текущего этапа)

Сейчас ТЗ содержит роли, функции с приоритетом и критериями «готово», требования и открытые вопросы. Нужно добавить:

- **Пользовательские истории** с критериями в форме «Дано / Когда / Тогда». Из них потом получаются тест-кейсы (6.1).
- **Матрица прав**: роль × действие × данные.
- **Нефункциональные требования** простыми словами: скорость, сколько пользователей, языки, устройства, доступность, где хранить данные, резервные копии, срок хранения.
- **Интеграции**: оплата, почта, мессенджеры, внешние системы; для каждой — кто даёт доступ.
- **Трассировка**: каждая функция ссылается на шаг процесса или решение из «Предложений функций»; каждый шаг процесса, который делает продукт, покрыт функцией. Непокрытое — замечание проверки.

**Готово, когда** по ТЗ можно оценить работу и проверить результат, не спрашивая автора.

**Сделано 25 ноября.** У функции — история, проверки «Дано / Когда / Тогда» и источники (`step:<сценарий>.<шаг>`, `suggestion:<ключ>`, `rule:privacy|signin`, `owner`). У ТЗ — матрица прав (роль × данные × смотреть/создавать/менять/удалять, свои или все), 8 нефункциональных требований, интеграции с тем, кто даёт доступ (старое поле `integrations` вычисляется из них). Черновик без ИИ размечает все шаги процесса, пишет историю и проверку на сценарий, права по типу участника. Проверка: ТЗ без разметки, непокрытый шаг, клиент видит чужие личные данные (безопасность) — важные; обязательная функция без проверок — мелкое. Экран ТЗ — вкладками. Проверки «Дано / Когда / Тогда» и права из матрицы собираются в план тестов (§4.10), матрица прав задаёт роли операций в контрактах API (§4.7).

**Сделано 26 ноября — матрица прав в экранах.**
- Шаблон экранов следует матрице: список — там, где роли можно смотреть данные; форма — где можно создавать или менять; «Мои: …» — когда роль видит только свои записи.
- В редакторе у каждого экрана есть блок «Что роли можно здесь по ТЗ». В нём права роли на данные функций экрана, а расхождения подсвечены красным.
- Проверка качества экранов сверяет их с матрицей. Важные замечания (безопасность): функция другой роли на экране, данные, с которыми роли ничего нельзя делать, список записей, которые роли нельзя смотреть, форма, которой роли нельзя пользоваться. Незначительное замечание: по ТЗ роли можно создавать данные, но ни на одном её экране нет формы для этого.
- Если в ТЗ нет матрицы прав (проекты, начатые раньше), этих проверок нет.

### 4.6. Архитектура (из «вычисляется» в «редактируется»)

Сейчас архитектура строится из принятых входов автоматически, человек пишет только заметки. Нужно:

- **Редактор схемы данных (ER):**
  - поля с типами: текст, число, дата, деньги, список статусов, ссылка;
  - обязательность и уникальность;
  - связи 1–1, 1–N и N–N; для N–N запись-связка создаётся сама;
  - тот же принцип, что в процессе: правка на схеме, через ИИ с предпросмотром, проверки с кнопкой «Исправить».
- **Компоненты** выбираются из каталога поддерживаемых: веб-клиент, сервер, база, файлы, очередь, почта, оплата. Это не свободный текст, поэтому нарисовать несуществующее нельзя.
- **Решения** (ADR): что выбрали, из каких вариантов, почему, что это меняет. Карточки выбора записываются сюда же.
- **Безопасность и модель угроз:** вход, роли, где секреты, что шифруется. Что в продукте ценно (деньги, личные данные, доступ), кто может навредить (недобросовестный клиент, бывший сотрудник, посторонний) и как; что этому мешает. Каждая угроза потом становится кейсом проверки (4.10).
- **Окружения:** тестовое и рабочее, где что работает.
- **Требования к результату:**
  - каждая сущность ТЗ есть в ER;
  - каждая функция покрыта компонентом;
  - каждое нефункциональное требование имеет решение;
  - каждый внешний сервис есть в интеграциях;
  - у каждой функции с деньгами или личными данными есть угрозы и меры против них.

**Готово, когда** разработчик или ИИ-агент может начать контракты, не задавая вопросов «где это хранить» и «через что это работает».

**Сделано 25 ноября — для веб-приложений.** Основа плана по-прежнему вычисляется из принятых этапов; поверх неё — проектные решения (`design` в содержимом этапа): схема данных (12 типов полей, обязательность, уникальность, ссылки, значения статусов; связи 1–1, 1–N, N–N, связка для N–N создаётся сама), компоненты из каталога из 17 (неизвестный отбрасывается), решения (варианты, выбор, почему, последствия, связь с нефункциональным требованием ТЗ), угрозы (что, кто, как, что мешает), окружения. Первый вариант платформа готовит без ИИ по процессу и ТЗ. Схема данных, компоненты и контракт API плана строятся из решений; приёмка сверяет с планом из тех же решений. Проверка: данные ТЗ без записи в схеме, нет сервера или базы, интеграция не стала компонентом, деньги или личные данные без угроз, угроза без меры (безопасность) — важные; требование без решения, решение не принято — мелкие. Экран — вкладками. У сайтов архитектуру и дальше строит платформа: сайт собирает она сама.

**Сделано 26 ноября — правка через ИИ и «Исправить».**
- «Изменить через ИИ» у архитектуры приложения. ИИ видит только то, что правят люди: проектные решения и заметки. Его ответ — предложение, показанное списком: что добавлено, изменено и убрано, плюс новые замечания проверки. Сохраняется только по кнопке «Применить». Сценарии, схему и контракт API платформа пересчитывает из предложенных решений сама. Компонент не из каталога ИИ добавить не может.
- «Исправить» у замечаний «данных нет в схеме», «нет сервера или базы», «интеграция не стала компонентом», «нет угроз для личных данных или денег». Кнопка добавляет то, что по тем же процессу и ТЗ нарисовала бы сама платформа: запись со связями, компонент, типовые угрозы с мерами. Остальные замечания («у угрозы нет меры», «решение не принято», «требование без решения») можно поручить ИИ кнопкой «Исправить с ИИ».

**Сделано 26 ноября — карточки выбора у приложений.** Во вкладке «Решения» у веб-приложения теперь четыре карточки (раньше была только «Где хранить код»). Пока владелец не выбрал, действует рекомендация платформы.
- **Технологии.** Вариант «Профиль BuildPath» (Node.js 20, React, PostgreSQL) — на нём ИИ-агент пишет и проверяет код. Вариант «Свой стек у разработчика»:
  - задачи ИИ-агента для проекта отклоняются;
  - шаблон плана реализации отдаёт все модули специалистам;
  - модуль, поручённый ИИ, — важное замечание плана.
- **Где будет работать приложение.** Render или свой сервер. У Render прямо написано, чего не даёт бесплатный тариф: сервис засыпает после 15 минут без посетителей, бесплатная база удаляется через 30 дней, сервера в Казахстане нет.
- **Адрес приложения.** Адрес хостинга или свой домен. При своём домене пункт «Свой адрес» в чек-листе запуска обязателен. Если проверен всё ещё адрес хостинга, появляется важное замечание.
- Принятые решения (не значения по умолчанию) попадают в пакет для разработки файлом `decisions.md`.

### 4.7. Контракты (новый)

- **Назначение.** Зафиксировать границы так, чтобы модули могли делать разные люди или ИИ одновременно и не сломать друг друга.
- **Входы.** ТЗ, архитектура.
- **Результат.**
  - **API** (OpenAPI): запросы, ответы, ошибки, права.
  - **Схема базы и миграции**, получаемые из ER.
  - **События и уведомления**: что, когда и кому.
  - **Интеграции**: какие вызовы и что при ошибке.
  - **Границы модулей**: какой модуль чем владеет.
- **Как работает.** Черновик строится из ER и функций (часть уже есть: черновик контракта API в архитектуре). ИИ дополняет ошибки и крайние случаи. Специалист по желанию проверяет. Владелец утверждает; это контракт в смысле STAGE_WORK_MODEL §22.
- **Требования к результату.**
  - Контракт проходит линтер.
  - Каждая функция ТЗ покрыта операцией.
  - Каждая операция имеет права из матрицы.
  - Все ошибки описаны.
- **Приёмка.** Автопроверки пройдены, владелец утвердил.
- **Готово, когда** по контракту можно писать модуль и автоматически проверять его соответствие.
- **Дальше →** План, модули. Изменение контракта — уведомление каждому модулю на нём.

**Сделано 25 ноября — для веб-приложений.** Этап `contracts` (каталог маршрутов 1.13.0) стоит между архитектурой и пакетом для разработки; входы — процесс, ТЗ, архитектура; пакет берёт контракты как вход. Черновик без ИИ строит платформа:
- модуль на каждую запись схемы данных, плюс «Аккаунты» (пользователь, регистрация, вход, текущий пользователь);
- операции списка, просмотра, создания, изменения и удаления — только там, где матрица прав ТЗ разрешает это действие хоть одной роли, и только этим ролям;
- ошибки 401 и 403, 404 у операций по адресу записи (при доступе «только свои» ответ одинаковый для «нет» и «чужая»), 400 и 409 по смыслу;
- события — из шагов процесса, где кого-то уведомляют, с получателем по виду шага;
- интеграции — из сервисов ТЗ с планом на сбой (оплата: заказ остаётся «ожидает оплаты»).

Проверка:
- одинаковая операция дважды — блокирует;
- функция ТЗ без операции, операция без прав, роль шире матрицы (безопасность), запись у двух модулей, сервис без плана на сбой или не описан — важные;
- нет ошибок, нет ответа 404, запись без модуля — мелкие.

Из сохранённой версии платформа пишет три файла, они же идут в пакет вместо черновика API из архитектуры:
- `openapi.yaml` (OpenAPI 3.1; права ролей — `x-roles`, без входа — только регистрация и вход);
- `schema.sql` (PostgreSQL: таблицы, обязательные и уникальные поля, допустимые значения статусов, внешние ключи после всех таблиц, таблицы-связки N–N);
- `contracts.md`.

Сгенерированный OpenAPI проходит линтер, миграция применяется к PostgreSQL 16. Экран — вкладками «Модули / Операции / События / Интеграции / Файлы». Старые проекты не меняются: маршрут сохраняется при создании проекта, их пакет берёт черновик API из архитектуры.

**Сделано 26 ноября — проверка модуля по контракту.** После проверки запуска платформа запускает собранное приложение ещё раз и обращается к каждой операции контрактов без входа:
- операция с ролями должна ответить 401;
- регистрация и вход должны отказать пустым данным;
- ни одна операция не должна отвечать 404, 405 или 5xx.

Результат записывается по каждой операции. Этап модуля смотрит только свои операции и не принимается, пока они не отвечают как обещано. Форма данных и правила после входа — по-прежнему задача кейсов плана проверки.

**Сделано 26 ноября — ИИ с предпросмотром.** По заданию владельца ИИ дополняет контракты: ошибки и крайние случаи операций, события, поведение при сбоях сервисов. Предложение ИИ показано списком по именам: что добавлено, изменено и убрано, плюс новые замечания проверки. Сохраняется только по кнопке «Применить». Документ проверяется целиком, поэтому отдельные части не защищаются от ИИ: защита — это сам предпросмотр. «Исправить с ИИ» у замечаний работает. Если ИИ дал операции права шире матрицы ТЗ, это видно в замечаниях ещё до сохранения.

### 4.8. План реализации (новый)

- **Назначение.** Ответить: из каких частей состоит работа, в каком порядке её делать, что можно параллельно, сколько стоит и когда будет.
- **Входы.** ТЗ, архитектура, контракты.
- **Результат.**
  - **Модули** (вход и роли, заявки, оплата, уведомления, админка…) с функциями внутри.
  - **Граф зависимостей**: что после чего; критический путь подсвечен; параллельные ветки видны на схеме.
  - **Выпуски**: первая версия, затем следующие, по приоритетам ТЗ.
  - **Оценка по модулям**: запросы к ИИ (деньги), часы специалиста, календарный срок.
  - **Кто делает**: ИИ-агент, специалист или ИИ под присмотром специалиста.
  - **Готово для каждого модуля**: контрактные тесты зелёные, критерии историй выполнены.
  - **Риски** из разбора идеи с действиями.
- **Как работает.** Платформа предлагает разбиение по контрактам; граф строится сам, ИИ и человек правят. Изменения — с предпросмотром на схеме, как в процессе.
- **Отслеживание хода работ.** План не только документ, а рабочий инструмент на весь срок реализации:
  - **дерево с отметками**: модуль → функция → задача; у задачи статус (не начата / в работе / на проверке / готова / заблокирована), исполнитель и срок;
  - **прогресс** у каждого модуля и у проекта в целом — по готовым задачам с учётом их веса (оценки), а не по числу пунктов;
  - **задача готова только по проверке**: её тест-кейсы (раздел 4.10) прошли, и это видно рядом с отметкой. Поставить «готово» руками без зелёных проверок нельзя, можно только «готово с замечанием» с объяснением, как при пропуске замечания проверки;
  - **блокировки видны**: задача ждёт другую задачу, контракт или ответ владельца — показано, кого и что ждём; на графе блокировка красная;
  - **критический путь и срок**: если задача на критическом пути опаздывает, платформа пересчитывает дату выпуска и пишет владельцу;
  - **факт против плана**: потрачено запросов к ИИ и часов специалиста против оценки по каждому модулю (данные уже есть в смете и табеле);
  - **на карте проекта** — общий прогресс и следующая важная задача; во «Входящих» у каждого — его задачи.
- **Требования к результату.**
  - Нет циклов в зависимостях.
  - Каждая функция первой версии в каком-то модуле.
  - У каждого модуля есть исполнитель и оценка.
- **Приёмка.** Владелец утвердил план и бюджет.
- **Готово, когда** каждый модуль можно отдать исполнителю отдельным этапом, а ход работ виден без вопросов исполнителям.
- **Дальше →** Модули (этапы реализации создаются из плана — карта проекта растёт). Отметки задач обновляются из модулей и проверок сами.

**Сделано 25 ноября — для веб-приложений.** Этап `roadmap` (каталог маршрутов 1.14.0) стоит после контрактов; входы — разбор идеи, ТЗ, архитектура, контракты; пакет для разработки получает `plan.md`.

Черновик без ИИ строит платформа:
- модули: «Каркас приложения» (репозиторий и проверки, база по `schema.sql`, окружение), модуль на каждый модуль контрактов и «Уведомления и интеграции»;
- задачи: из операций API, по одной на функцию ТЗ (оценка растёт с числом «готово, когда»), из событий и интеграций;
- порядок: «Аккаунты» — раньше всех модулей, запись, которая ссылается на другую, — после неё; остаются только прямые зависимости;
- выпуски — по приоритетам ТЗ;
- риски — из разбора идеи;
- исполнитель: ИИ-агент, ИИ под присмотром специалиста, специалист (оплата — специалисту).

Срок, параллельные ветки, критический путь и итоги по выпускам вычисляются, а не хранятся.

Проверка:
- цикл — блокирует;
- обязательная функция или модуль контрактов не в плане, пустой модуль, задача без часов — важные;
- порядок выпусков, нет рисков, риск без действия — мелкие.

Экран — вкладками, граф модулей с критическим путём красным пересчитывается при правке.

После утверждения в плане отмечают ход работ (таблица `plan_task_states`):
- у задачи — статус, исполнитель, срок, замечание или что ждёт;
- прогресс считается по часам оценки;
- ожидаемое окончание — сегодня плюс оставшиеся часы критического пути в рабочих днях;
- показаны блокировки, опоздания и следующая важная задача;
- запросы к ИИ и часы по табелю считаются с утверждения против плана.

«Готова» ставится только по зелёным проверкам задачи. Пока проверок нет (они появятся с планом тестов, §4.10), сервер отказывает, и закрыть задачу можно только как «готова с замечанием» с письменной причиной.

**Сделано 26 ноября — срок и задачи.**
- При принятии плана фиксируется обещанный срок.
- Срок пересчитывается каждый час и после каждого изменения задачи.
- Если срок уходит на 2 рабочих дня и больше позже того, о чём уже сообщали, владелец и менеджеры получают сообщение в Telegram или на почту — по своим настройкам. В нём: обещанный и нынешний срок, сколько часов осталось на критическом пути, какие его задачи опаздывают и что можно сделать.
- Повторно сообщение приходит только при новом сдвиге.
- Во «Входящих» владельца и менеджеров пункт «Срок» висит, пока срок позже обещанного.
- Исполнитель видит во «Входящих» свои незавершённые задачи плана с ближайшим сроком.
- В ходе работ плана рядом с прогнозом показан обещанный срок.

Прогресс на карте проекта виден по этапам модулей (§4.9).

**Сделано 26 ноября — ИИ с предпросмотром.** ИИ меняет план по заданию владельца: задачи, оценки, исполнителей, выпуски, риски. Граф, критический путь и срок пересчитываются сами. Предложение ИИ показано списком по именам: что добавлено, изменено и убрано, плюс новые замечания проверки. Сохраняется только по кнопке «Применить». Документ проверяется целиком, поэтому отдельные части не защищаются от ИИ: защита — это сам предпросмотр. «Исправить с ИИ» у замечаний работает.

### 4.9. Модуль (этап реализации, по одному на модуль)

- **Входы.** Контракты, план, связанные модули (только их контракты, не код).
- **Как работает.** ИИ-агент пишет код модуля в изолированной среде, в своей ветке модуля. Специалист направляет его или пишет сам — по режиму доступа. Платформа гоняет проверки качества, кейсы плана проверки и проверку операций по контрактам.
- **Приёмка.**
  - Контрактные тесты зелёные.
  - Критерии историй модуля выполнены.
  - Проверки качества без блокирующих замечаний.
  - Специалист (если есть) и владелец приняли.
- **Готово, когда** модуль можно соединить с остальными без правки чужих модулей.

**Сделано 25 ноября — первая часть (веб-приложения).** Модуль плана реализации можно поручить ИИ-агенту прямо из хода работ. Задачу агенту пишет платформа по плану, контрактам и плану проверки: модуль, на какие модули он опирается (их не менять), его задачи, операции API и кейсы, которые должны пройти. Агент работает поверх последнего кода или с пустой папки. Незаконченные задачи модуля становятся «в работе».

Агент получает контракты, план и автоматические кейсы плана проверки. Тесты он пишет на `node:test`, и в названии каждого — `[case:<ключ>]`.

После задачи платформа сама запускает `node --test --test-reporter=tap` (проверка «Кейсы плана проверки проходят», информационная) и отмечает автоматические кейсы:
- задача плана, у которой все кейсы прошли, становится «готова» сама;
- «готова», у которой кейс упал, возвращается «в работу»;
- «готова с замечанием» — слово владельца, её прогон не трогает;
- кейс человека прогон не трогает, а человек не может отметить автотест.

**Сделано 26 ноября — ветка кода на модуль и основная линия.**
- У каждого модуля своя ветка кода. Задача агента по модулю продолжает собственный последний результат модуля. Новая ветка начинается с основной линии кода проекта, а до первого принятого модуля — с пустой папки. Незаконченная работа другого модуля никогда не становится основой.
- Основная линия — код проекта из принятых модулей. При принятии этапа модуля платформа вливает его код в основную линию трёхсторонним слиянием: текст построчно, JSON по ключам. Так два модуля, добавившие свои зависимости в `package.json`, не мешают друг другу.
- Новую версию основной линии платформа собирает и проверяет как результат агента: установка, тесты, сборка, запуск, контракты. ИИ в этом не участвует, денег не списывается.
- Если модуль и основная линия поменяли одни и те же строки, платформа не выбирает за людей. Этап модуля нельзя принять даже с объяснением, на странице модуля видно, какие файлы конфликтуют. Кнопка «Согласовать с основной линией» отдаёт агенту слитый код с пометками конфликтов, агент сводит обе версии. Код с оставшимися пометками в основную линию не попадёт.
- В репозитории владельца одна ветка на модуль (`buildpath/module-<ключ>`) и одна для основной линии (`buildpath/main-line`). Повторная отправка обновляет тот же запрос на слияние. Агент в сети клиента отправляет код в те же ветки.

Ограничение: ИИ-агент по-прежнему выполняет одну задачу проекта за раз. Модули идут в своих ветках независимо, но задачи агента по ним выполняются по очереди.

**Сделано 25 ноября — модули как этапы (решение 3).** Каждый модуль принятого плана реализации — отдельный этап `m_<модуль>` с названием модуля (каталог маршрутов 1.17.0).
- Этапы появляются при принятии плана. У проектов, где план уже был принят, — при первом открытии проекта.
- На карте модули стоят после пакета для разработки и перед запуском, в одной строке: их делают параллельно.
- Входы модуля — контракты, план реализации и план проверки. Модуль открывается, когда они приняты. Их изменение приходит каждому модулю уведомлением.
- Новая версия плана добавляет и переименовывает модули. Модуль, которого больше нет в плане, удаляется, если над ним не работали. Если работали — откладывается: сделанное сохранено, и этап продолжится, когда модуль вернут.
- У этапа модуля свой исполнитель: владелец, участник или приглашённый на этот этап специалист. Он видит задачи агента по своему модулю и может поручить модуль агенту.
- На странице модуля: что за модуль, на какие модули он опирается и кто опирается на него, его задачи и кейсы с результатами, агент и поле «Что сделано — для приёмки».
- Приёмку проверяют живые данные:
  - не готовые задачи, упавшие кейсы, непройденные проверки последней сборки и модуль вне плана — блокирующие замечания;
  - «платформа ещё не собирала модуль» — важное;
  - задача без кейсов — мелкое.
  Блокирующее можно принять только с письменным объяснением, как на других этапах.
- Подготовка к запуску показывает непринятые модули важным замечанием. Запуск они не блокируют: готовность решают кейсы плана проверки.

**Сделано 25 ноября — ИИ-агент в браузере и код теста.**

ИИ-агент в браузере проверяет кейсы с таким способом проверки на последнем предпросмотре, который собрал агент. Предпросмотр — настоящий клиент на данных в памяти, с демо-входом по ролям.
- Предпросмотр открывается в Chromium на экране телефона; любые запросы со страницы наружу отклоняются.
- Агент видит текст экрана и пронумерованные элементы, нажимает, вводит, выбирает. Решение — «работает», «не работает» или «не удалось проверить» — он даёт с тем, что увидел.
- Без решения за отведённые шаги — «не удалось проверить», никогда не «работает».
- Результат записывается с пометкой «ИИ-агент в браузере», но не поверх результата человека.
- Это проверка интерфейса и правил на предпросмотре, а не рабочего сервера. Так и написано в интерфейсе.

У каждого автоматического кейса есть «Код теста»: тест агента с ключом кейса в названии, с файлом и строкой.

### 4.10. План проверки, инструкции для проверки и приёмка владельцем (новые)

Проверка строится заранее, а не после того, как код готов. Каждый тест-кейс — это одновременно **инструкция для человека** (что сделать по шагам и что должно получиться) и **описание для автотеста**. Один и тот же кейс проверяет и ИИ-агент, и специалист по тестированию, и владелец.

**Откуда берутся кейсы.**
- Истории ТЗ «Дано / Когда / Тогда» → кейсы нормального пути.
- Сценарии процесса и «Вы это учли?» → кейсы для ответов владельца (отмена, перенос, сотрудник уволился).
- Матрица прав → кейсы «кому нельзя».
- **Модель угроз** с архитектуры (новая часть этапа «Архитектура»: что ценно, кто может навредить и как) → кейсы недобросовестного пользователя и безопасности.
- Нефункциональные требования → кейсы нагрузки, скорости, устройств, доступности.

**Классы кейсов.** Для каждой функции первой версии план проверки должен содержать кейсы каждого подходящего класса; пустой класс — замечание проверки с вопросом «почему не нужно».

| Класс | Кто | Примеры для онлайн-записи |
|---|---|---|
| **Нормальный путь** | Добросовестный пользователь делает всё правильно | Клиент выбирает услугу и время, записывается, получает подтверждение |
| **Ошибки и невнимательность** | Добросовестный, но ошибается | Неверный телефон, двойное нажатие «Записаться», закрыл вкладку посередине, ввёл время в прошлом, плохой интернет |
| **Крайние случаи** | Редкие, но законные ситуации | Последнее свободное окно берут двое одновременно, запись на полночь, смена часового пояса, очень длинное имя, эмодзи |
| **Недобросовестный пользователь** | Пытается получить больше, чем положено | Записывается на все окна и не приходит, отменяет чужую запись по подобранной ссылке, меняет цену в запросе, обходит лимит, оставляет спам в форме, подставляет чужой телефон |
| **Права и роли** | Пользователь видит или делает чужое | Сотрудник открывает записи другого мастера по ссылке, клиент заходит в админку, уволенный сотрудник входит после отключения |
| **Безопасность** | Атака на продукт | Внедрение кода в поля (XSS, SQL), подбор пароля, кража сессии, загрузка вредного файла, перебор ID в адресе, CSRF, утечка персональных данных в ошибках и логах |
| **Данные и закон** | Персональные данные | Клиент просит удалить данные — удалены везде; согласие записано; данные не уходят в чужие сервисы |
| **Сбои и восстановление** | Внешние сервисы и инфраструктура | Почта или оплата не отвечает, база перезапустилась, восстановление из резервной копии |
| **Нагрузка и скорость** | Много людей сразу | 200 записей в минуту в день акции, медленный телефон |
| **Устройства и доступность** | Разные люди и экраны | Телефон, планшет, компьютер, крупный шрифт, экранный диктор, только клавиатура |

**Что в каждом кейсе (инструкция для проверки).**
- Название и класс.
- Кто действует: роль, добросовестный или нет.
- Исходное состояние: «Дано».
- Шаги по порядку: «Когда».
- Ожидаемый результат: «Тогда» — что видит пользователь, что сохранено, что *не* должно произойти.
- Связь: какая история, функция, правило или угроза проверяется.
- Как проверяется: автотест, ИИ-агент в браузере, человек.
- Важность: блокирует запуск или нет.

**Как работает этап.**
1. Платформа собирает черновик кейсов из источников выше по шаблонам классов.
2. ИИ дополняет отраслевыми случаями злоупотреблений и помечает их «предложение ИИ».
3. Специалист по тестированию или безопасности (по желанию владельца) проверяет и дополняет.
4. Владелец видит итог простыми словами: «Мы проверим, что клиент не сможет отменить чужую запись». Ему не нужно читать технические кейсы.

**Требования к результату.**
- Каждая функция первой версии покрыта кейсами нормального пути, ошибок и прав.
- Каждая функция с личными данными или деньгами покрыта кейсами недобросовестного пользователя и безопасности.
- Каждая угроза из модели угроз покрыта хотя бы одним кейсом.
- Нет кейсов без ожидаемого результата.

**Прогон проверок** (этап «Сборка и автоматические проверки», 6.2, и каждый модуль):
- автотесты по кейсам пишет ИИ-агент вместе с кодом модуля;
- платформа добавляет свои проверки: статический анализ безопасности, зависимости с известными уязвимостями, заголовки безопасности, скорость, доступность;
- результат по кейсам виден в плане: какие пройдены, какие упали, какие проверяет человек и ещё не проверил. Отсюда же — отметки задач в плане реализации (4.8).

**Честность.** Автоматические проверки не заменяют аудит безопасности. Для продуктов с деньгами и личными данными платформа рекомендует специалиста по безопасности и так и пишет. Пройденные проверки не называются «сертификатом» (CLAUDE.md).

**Приёмка владельцем.** Тестовая версия и список главных сценариев из плана проверки, по классам «нормальный путь» и «ошибки». По каждому владелец отмечает «работает», «не работает» или «замечание». Замечание становится задачей модуля в плане.

**Готово, когда** все блокирующие кейсы пройдены, проверки безопасности без критичных находок (или с записанным решением владельца), главные сценарии приняты владельцем.

**Сделано 25 ноября — для веб-приложений (план проверки).** Этап `testplan` (каталог маршрутов 1.15.0) стоит после плана реализации; пакет для разработки получает `test-plan.md`.

Черновик без ИИ строит платформа:
- нормальный путь — из «Дано / Когда / Тогда» ТЗ или его «готово, когда»;
- ошибки — пустое или неверное поле, двойное нажатие;
- права — роль, которой матрица не разрешает действие, пробует прямой запрос (403); «только свои» отвечают 404, как несуществующие;
- угрозы архитектуры — по кейсу на каждую;
- подбор пароля, XSS, CSRF;
- при личных данных — удаление по просьбе и данные вне ошибок и журналов;
- сбой каждой интеграции контрактов и восстановление из копии;
- ответы «Вы это учли?» как правила;
- нагрузка — по нефункциональным требованиям;
- телефон, клавиатура и экранный диктор.

У кейса:
- кто действует и добросовестный ли он;
- дано, шаги, тогда, «не должно»;
- как проверяется: автотест, ИИ-агент в браузере или человек;
- блокирует ли запуск;
- что он проверяет и к какой задаче плана реализации привязан;
- фраза для владельца «Мы проверим, что…».

Проверка:
- у обязательной функции нет нормального пути или «кому нельзя» — важное;
- угроза не покрыта (безопасность) — важное;
- при личных данных или деньгах нет кейсов недобросовестного пользователя и безопасности (безопасность) — важное;
- у кейса нет ожидаемого результата — важное;
- нет кейса ошибки, нет шагов, пустой класс без объяснения — мелкие.

Результаты:
- результаты кейсов, которые проверяет человек или ИИ-агент в браузере, отмечает человек (таблица `plan_case_results`, «не работает» — с описанием);
- автотесты получают результат только из прогона;
- задача плана реализации становится «готова», только когда все её кейсы пройдены по текущей версии плана проверки, иначе — «готова с замечанием» с причиной.

Прогон автотестов, проверка кейсов ИИ-агентом в браузере и приёмка владельцем главных сценариев сделаны на шаге 9а (§4.9).

**Сделано 26 ноября — ИИ с предпросмотром.** По заданию владельца ИИ добавляет кейсы, например типичные для отрасли злоупотребления клиентов, бывших сотрудников и посторонних. Кейсы от ИИ помечены «от ИИ», что бы он ни указал сам; у существующих кейсов автор не меняется. Предложение ИИ показано списком по именам: что добавлено, изменено и убрано, плюс новые замечания проверки. Сохраняется только по кнопке «Применить». Документ проверяется целиком, поэтому отдельные части не защищаются от ИИ: защита — это сам предпросмотр. «Исправить с ИИ» у замечаний работает.

Модель угроз в архитектуре уже есть (сделано вместе с редактором архитектуры).

**Сделано 25 ноября — приёмка владельцем.** Владелец или менеджер проходят главные сценарии — кейсы классов «нормальный путь» и «ошибки» — в тестовой версии. По каждому они отмечают «работает», «работает, есть замечание» или «не работает»; для двух последних нужно описание.

Замечание и «не работает» становятся задачей плана реализации:
- задача видна в ходе работ модуля как «замечание владельца», без оценки;
- «работает» по тому же сценарию её закрывает.

«Готовность к запуску» показывает правило «Готово, когда»: блокирующие кейсы пройдены, главные сценарии приняты, открытых замечаний нет.

### 4.11. Подготовка к запуску (расширение)

Чек-лист с проверками платформой:
- домен и HTTPS;
- почта для уведомлений;
- юридические тексты: политика, оферта, согласие;
- резервные копии и проверка восстановления;
- мониторинг и кому писать при сбое;
- перенос данных из старой системы, если есть;
- аналитика целей успеха из 4.2.

**Готово, когда** продукт можно открыть людям, а сбой не останется незамеченным.

**Сделано 25 ноября — для веб-приложений.** Этап `launch` (каталог маршрутов 1.16.0) стоит после пакета для разработки, у него своя фаза «Запуск» на карте.

Платформа проверяет:
- правило плана проверки: блокирующие кейсы пройдены, главные сценарии приняты, замечаний нет;
- последнюю проверку адреса: отвечает, по HTTPS, с настоящей базой, а не в памяти.

Непройденная проверка — блокирующее замечание: этап принимается только после исправления или с письменным объяснением владельца, и оно остаётся в журнале.

Владелец отмечает восемь пунктов: домен, юридические тексты, почта, резервные копии с проверкой восстановления, мониторинг, перенос данных, цифры успеха (из целей разбора идеи), аудит безопасности. У пункта три состояния: «готово», «не нужно» с причиной, «ещё не сделано».

Пункты, без которых этому приложению нельзя, не могут быть «не нужно»:
- копии и мониторинг — всегда;
- юридические тексты — при личных данных;
- почта — если приложение отправляет письма.

Без аудита при деньгах и личных данных видно «проверено автоматически, аудит не проводился». У сайтов подготовка к запуску по-прежнему внутри публикации.

**Сделано 26 ноября — слежение за запущенным приложением.** После принятия этапа запуска платформа сама следит, отвечает ли приложение:
- каждые 10 минут открывает `/api/health` по адресу, который проверяли при передаче кода;
- если адрес в закрытой сети, проверяет агент в сети владельца (программа 1.1.0 и новее с заданным APP_URL) и присылает результат. Старый агент проверок не шлёт, и на странице об этом сказано;
- две неудачные проверки подряд — «не работает»: открывается сбой, владельцу приходит письмо или сообщение в Telegram (категория «сайт»), в журнале событие;
- первая удачная проверка закрывает сбой, владелец получает «снова работает» и сколько не работало;
- на этапе запуска видно состояние, кто проверяет, последнюю проверку, причину и последние 5 сбоев. Если проверок нет больше 30 минут, об этом предупреждение.

Внешний мониторинг (пункт чек-листа) по-прежнему нужен: платформа видит только, отвечает ли `/api/health`, а не ошибки внутри приложения, нагрузку и место на диске.

### 4.12. Развитие (расширение)

- **Бэклог.** Отложенные функции («потом»), замечания после запуска и отзывы пользователей в одном списке с приоритетами.
- **Следующая версия.** Выбранные пункты бэклога проходят тот же путь. Платформа показывает, какие этапы затронуты, и не заставляет проходить остальные заново.

**Сделано 25 ноября.** Вкладка «Развитие» на странице проекта, таблица `backlog_items`.

Список пополняется сам, без перезаписи уже записанного:
- функции ТЗ с приоритетом «позже»;
- предложения с решением «потом»;
- открытые замечания владельца к главным сценариям.

Отзывы людей и свои идеи добавляются вручную, с важностью «важно», «обычно» или «когда-нибудь». Пункт можно отметить «Уже сделано» или «Не будем делать» и вернуть обратно.

«Начать версию N» (может владелец или менеджер, когда ТЗ принято):
- выбранные пункты получают номер версии;
- ТЗ снова открывается, а на его странице появляется блок «Новая версия N: добавьте в ТЗ»;
- после принятия нового ТЗ следующие этапы получают обычные уведомления об изменениях, и переделывать нужно только затронутое.

API: `GET/POST /projects/{id}/backlog`, `PUT /projects/{id}/backlog/{itemId}`, `POST /projects/{id}/backlog/next-version`.

**Сделано 26 ноября — отзывы из приложения.** На вкладке «Развитие» владелец включает приём отзывов. После этого:
- ИИ-агент добавляет в приложение ссылку «Сообщить о проблеме или идее» с короткой формой. Форма отправляет только то, что человек написал: вид, текст, по желанию контакт и страницу. В демо-предпросмотре она ничего не отправляет.
- Сообщения сами становятся пунктами бэклога с пометкой «из приложения»: проблема — важная, идея — обычная. Текст хранится как обычный текст и ИИ не передаётся.
- Защита: адрес приёма принимает только сообщения, без сессии; поле-ловушка для ботов; не больше 10 сообщений в час с одного адреса и 300 в день на приложение. Адрес можно выключить или сменить — старый сразу перестаёт работать.

Ограничения:
- Приложение, собранное раньше, получит форму со следующей задачей агента или от разработчика.
- Нужен заданный `PUBLIC_API_URL` у API.

**Сделано 27 ноября — аналитика использования.** Решение владельца: данные хранятся на платформе. На вкладке «Развитие» блок «Сколько людей пользуется»; подсчёт включает владелец.

- **Что попадает в приложение.** Когда подсчёт включён, ИИ-агент добавляет пару строк `navigator.sendBeacon`:
  - `kind=view` с путём экрана при каждой смене экрана;
  - `kind=action` с названием из 2–4 слов, когда удалось главное действие: заявка, заказ, запись. Не больше 10 видов.

  Больше ничего не отправляется: ни id, ни почты, ни имён, ни текстов, ни параметров адреса. В демо-предпросмотре строки ничего не шлют.
- **Что хранит платформа.** Только счётчики по дням: открытия экранов, главные действия, посетители.
  - Cookie, хранилища браузера, id пользователей и IP-адресов нет.
  - Посетитель считается один раз в день по хешу адреса и браузера с солью дня. Соль и хеши удаляются на следующий день, поэтому узнать человека или проследить его между днями нельзя. Число посетителей примерное.
  - Счётчики старше 400 дней удаляются.
- **Защита от лишнего.**
  - Путь очищается: без параметров, номера, uuid, длинные коды и почта заменяются на `:id`, не длиннее 80 знаков.
  - Боты и запросы без браузера не считаются.
  - После 60 разных названий в день остальное считается вместе как «…».
  - Лимиты: 600 запросов в час с одного адреса и 50 000 в день на приложение.
  - Адрес можно выключить или сменить. Старый сразу перестаёт считать, накопленные цифры остаются.
- **Отчёт за 7 или 30 дней:** посетители, открытия экранов, главные действия, столбики по дням, самые открываемые экраны и действия.
- **API.**
  - `GET/PUT /projects/{id}/usage` — отчёт и включение;
  - `POST /usage/{token}` — публичный адрес приёма, без сессии, CORS `*`.

Ограничения:
- Только для веб-приложений.
- Приложение, собранное раньше, начнёт считать со следующей задачи агента или после правки разработчика: адрес для него — в блоке «Адрес для разработчика».
- Цифры успеха из разбора идеи с этими счётчиками пока не сравниваются.

### 4.13. Путь клиента (новый этап сайтов, сделан 26 ноября)

У приложения опыт пользователя — экраны и прототип. У сайта не было этапа, где видно, как посетитель доходит до заявки. Теперь он есть: `paths`, каталог маршрутов 1.19.0.

- **Где.** На всех маршрутах сайтов, после ТЗ и страниц, каталога или расписания, перед архитектурой. Фаза «Опыт пользователя». Этап можно пропустить, если сайт простой.
- **Что записывается.** До пяти путей. В каждом пути:
  - кто посетитель;
  - откуда пришёл: поиск, карты, реклама, соцсети, мессенджер, совет знакомых, QR-код, другое;
  - чего хочет — одна фраза;
  - до шести шагов по сайту: страница или блок и что там видно;
  - чем заканчивается путь: звонок, сообщение, заявка, почта, визит, онлайн-запись (только у сайта с записью) или заказ (только у магазина);
  - что может остановить посетителя и что на сайте на это отвечает.
- **Схема.** Каждый путь показан цепочкой: откуда → шаги → действие. Под ней сомнение и ответ.
- **Черновик.**
  - Без ИИ — по одному пути на группу клиентов из разбора идеи (или клиентов из «Цели»), через страницы сайта к главному действию. Сомнения не придумываются.
  - ИИ делает то же по разбору идеи, ТЗ и страницам.
- **Проверка.**
  - больше четырёх шагов до действия — важное замечание;
  - действие, которого сайт не умеет — важное замечание;
  - сомнение без ответа — важное замечание;
  - ни одного записанного сомнения — мелкое замечание.

  Обязательны «кто», «чего хочет», хотя бы один шаг и действие.
- **Дальше.** Пути — вход этапа «Структура и тексты». ИИ ставит блоки в порядке пути, ведёт к действию и отвечает на сомнения только записанными ответами. Пути попадают в `project.md`. Изменение путей присылает текстам уведомление.
- **Старые проекты не меняются:** у них этого этапа нет.

## 5. Сокращённые маршруты

Не всем нужна вся цепочка. Маршрут зависит от типа проекта; этапы можно пропускать с объяснением.

| Тип | Маршрут |
|---|---|
| Лендинг, сайт компании | Идея → Разбор (короткий) → Процесс → Функции → Концепция → ТЗ (короткое) → Наполнение и вид → Сборка → Запуск |
| Магазин, онлайн-запись | Как сайт, плюс Каталог / Расписание, Архитектура, Приёмка владельцем |
| Веб-приложение | Полная цепочка: Идея → … → Контракты → План → Модули → Проверка → Запуск → Развитие |
| Свой проект с готовыми материалами | Старт с любого этапа (STAGE_WORK_MODEL §10): загрузка → разбор → пробелы → Концепция собирается всё равно |

## 6. Проверка пробелов на каждом этапе

Механизм уже есть: проверка качества этапа, «Вы это учли?», ИИ-рецензент, «Исправить», «Изменить через ИИ» с предпросмотром. Его нужно распространить на новые этапы по одному принципу:

1. **Правила программы.** Детерминированные проверки структуры, полноты и связей. Блокирующие останавливают приёмку.
2. **Вопросы «Вы это учли?»** по типу проекта и отрасли. Это решения владельца, ИИ их не принимает.
3. **ИИ-рецензент.** Ищет то, что правила не ловят: противоречия с прошлыми этапами, пропущенные случаи. Даёт советы, этап не блокирует.
4. **Сквозная трассировка.** Цель → процесс → функция → компонент → контракт → модуль → тест-кейс. Разрыв в цепочке становится замечанием на том этапе, где он появился.

| **Агент BuildPath в сети клиента** (рекомендую) | Клиент запускает небольшой контейнер внутри своей сети. Агент сам подключается наружу к BuildPath (только исходящее HTTPS-соединение) и выполняет задания: отправить код во внутренний git, развернуть на внутренний сервер, проверить, что сайт открывается | Входящих портов и VPN не нужно. Ключи и пароли остаются у клиента. Так устроены раннеры GitHub/GitLab и туннели Cloudflare | Нужно сделать и поддерживать агента; клиент должен его установить |
| Постоянные исходящие IP BuildPath | Клиент разрешает доступ с адресов BuildPath в своём файрволе | Просто для клиента | На бесплатном Render постоянных исходящих адресов нет; открывает доступ всему BuildPath, а не одному проекту |
| VPN от BuildPath в сеть клиента (WireGuard, OpenVPN) | Сервер BuildPath подключается к VPN клиента | Привычно для админов | Опасно для платформы, где проекты разных клиентов: ошибка изоляции открывает чужую сеть. Сложно в бесплатной облачной инфраструктуре. **Не рекомендую** |
| SSH через промежуточный сервер (bastion) | Клиент даёт публичный сервер-шлюз, через него — во внутреннюю сеть | Работает с уже существующей инфраструктурой | Нужен публичный шлюз; подходит только для SSH-операций |

Что важно при любом варианте:
- **Генерация кода** (изолированная среда E2B) во внутреннюю сеть не ходит. Если коду нужны внутренние пакеты или реестр, нужно зеркало или агент.
- **Реальные данные клиента** платформа не хранит (решение владельца). Проверки на рабочей системе внутри сети выполняет агент и отправляет наружу только результат.
- Доступ агента выдаётся на проект и ресурс, со сроком. Каждое действие пишется в журнал (STAGE_WORK_MODEL §25).

**Предложение:** вариант «Агент» как способ «Свой путь» в карточках «Хранение кода» и «Развертывание». До него — честная пометка в карточках: «внутренняя сеть пока не поддерживается, используйте пакет и выкладку вручную».

**Сделано 25 ноября — агент в сети клиента (шаг 11), для веб-приложений.**
- В карточке «Где хранить код» есть вариант «Агент в вашей сети». На странице «Пакет для разработки» — блок агента:
  - ключ (показывается один раз);
  - программа для скачивания и команды запуска через Node.js или Docker;
  - состояние агента, задания и их результаты.
- Агент — один файл на Node.js 22 с git. Он сам обращается к BuildPath по HTTPS и ждёт задания: входящих портов и VPN не нужно.
- Заданий три, и BuildPath не присылает ни команд, ни адресов — агент работает с тем, что задано у него:
  - проверить приложение (`/api/health`);
  - отправить код сборки ИИ-агента во внутренний git отдельной веткой;
  - запустить команду выкладки владельца.
  Задание, на которое агент не настроен, платформа не создаёт. Отправку кода и выкладку владелец подтверждает.
- Пароли и ключи от git и серверов остаются у клиента. Вывод выкладки уходит в BuildPath, только если владелец это разрешил, и ключ в нём закрыт.
- Ключ один на проект: хранится хэш, срок — 180 дней. Новый ключ отзывает старый, отозванный ключ останавливает агента.
- Каждое действие пишется в журнал.
- Проверка агентом изнутри сети засчитывается в подготовке к запуску. Адрес без HTTPS остаётся блокирующим замечанием.

Пока не сделано:
- агента для сайтов;
- агента для проверок по плану на рабочей системе внутри сети;
- обновления агента одной командой;
- репозитория пакетов и зеркала для кода ИИ-агента — он по-прежнему пишется в облаке и не видит внутренних пакетов.

## 11. Схемы: как у известных инструментов, но без рисования вручную

Ориентиры: Lucidchart и BPMN (дорожки по участникам, начало и конец процесса, автоматическая раскладка), dbdiagram, DrawSQL и ChartDB (таблицы с полями и ключами, нотация «воронья лапка», автораскладка, подсветка связей при выборе таблицы).

Наш принцип отличается от них: человек не рисует фигуры, а заполняет структуру. Схема всегда строится из данных этапа, поэтому нарисовать бессмысленную или несогласованную схему нельзя. От инструментов берём удобство работы с холстом и привычные обозначения.

**Холст (общий для всех схем).**
- Масштаб: «−», «+», «вписать»; щипок двумя пальцами и колесо с Ctrl.
- Перемещение перетаскиванием.
- Полноэкранный режим.
- Скачать SVG и PNG.
- Легенда обозначений.
- На телефоне по умолчанию «вписать по ширине», крупные области нажатия.

**Процесс.**
- Дорожки по участникам. Значок начала процесса — круг, конца — жирный круг с результатом сценария.
- У каждого шага метка «сделает продукт» или «вручную».
- Выбор блока подсвечивает его и открывает правку (сделано).
- Цветом показаны изменения от ИИ (сделано) и замечания проверки (сделано).
- Ветвления «если… то…» — позже, отдельным шагом: нужна правка модели процесса.

**Схема данных (ER).**
- Таблица — карточка: название, поля с типом, метки «ключ» и «ссылка».
- Связи нотацией «воронья лапка»: «много» — лапка, «один» — черта.
- Автораскладка в сетку, связанные таблицы рядом.
- Выбор таблицы подсвечивает её связи и приглушает остальные.
- То же для архитектуры (типы полей уже есть) и, позже, для контрактов.
